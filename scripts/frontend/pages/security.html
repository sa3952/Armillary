安全 · SECURITY

每一項保護，都附上查證的方法。

〈信任〉回答「這些承諾由誰執行、你憑什麼相信」。這一頁回答「它實際怎麼運作、擋住了什麼、壞掉的時候會怎樣」。每一項都寫成三件事：本站怎麼做、它讓攻擊者或追蹤者做不到什麼、你怎麼自己查。數值全部照實列，包括我知道的弱點。

沒有第三方安全認證，沒有專業滲透測試，沒有漏洞獎金計畫。有的是可以逐行核對的設定、每次發布都在主機上重跑的驗收，以及一份誠實的攻擊面清單。

00重點

  1. 只走加密連線。HTTPS 只接受 TLS 1.2 與 1.3，瀏覽器被要求一年內只用加密連線（HSTS）。保護：同一個 Wi-Fi 或網路業者看不到、也改不了你送出的出生資料。
  2. 不追蹤。不設 cookie、不用瀏覽器儲存，沒有分析、廣告或錯誤追蹤程式，不向任何第三方發出請求。保護：沒有分析或廣告公司知道你來過，本站也沒有任何識別碼能把你的兩次造訪連起來。
  3. 瀏覽器只准執行本站自己的程式。內容安全政策（Content-Security-Policy）擋掉其他來源的程式與連線。保護：就算有人設法把程式碼混進頁面，瀏覽器也拒絕執行；頁面發出的連線只能回到本站。
  4. 伺服器不記你的 IP，也不記出生資料。存取日誌關閉；事件日誌只有 11 個固定欄位，約一週後自動刪除。保護：主機上沒有一份「誰在什麼時候查了什麼」的名單可以外洩、被要求交出，或被拿去分析。
  5. 計算程式關在沒有對外網路的容器裡。唯讀檔案系統、非 root 使用者、Linux 特權全部移除。保護：即使程式有漏洞被利用，它也沒有路把資料送出去，也改不了自己的程式檔。
  6. 主機只開必要的門。防火牆預設拒絕連入；管理登入只收金鑰、只接受受限來源；作業系統安全更新每天自動安裝。保護：網路上不停在猜密碼的程式，在這裡沒有密碼可猜；已公布修補的系統漏洞不必等人手動處理。
  7. 線上版本對得回公開原始碼。每張盤的計算收據印出這次用的程式版本；前端可以從公開原始碼重算出同一個雜湊。保護：你不必只聽我說「線上跑的就是公開的那份」。

這七項是降低風險，不是保證沒有漏洞。每一項的界線寫在它自己的說明裡，整體的弱點在第 14 節。

01七項保護，逐項查證

下面每一項都分成「本站怎麼做」「擋住什麼」「你怎麼查」。技術依據收在每一項最後，點開才看得到。

一、只走加密連線

本站怎麼做
所有連線都走 HTTPS。輸入 http:// 會被永久轉到 https://，轉址時丟掉網址 ? 後面的參數。加密協定只接受 TLS 1.2 與 1.3。回應帶 Strict-Transport-Security: max-age=31536000（HTTP 嚴格傳輸安全，HSTS）：瀏覽器看過一次之後，一年內會自己把 http 改成 https。
擋住什麼
同一個 Wi-Fi 的其他人、網路業者或中間設備看得到你連上本站，看不到、也改不了你送出的出生資料與收到的星盤。TLS 1.2 只提供具前向保密（forward secrecy）的金鑰交換：就算日後有人拿到本站的私鑰，也解不開以前錄下的連線。舊版的 TLS 1.0／1.1 會被拒絕。
你怎麼查
在終端機（terminal）執行下面兩行，第一行應印出 HSTS 標頭，第二行應印出這次連線用的 TLS 版本： 
curl -sI https://projectarmillary.com/zh-TW/ | grep -i strict-transport-security
curl -sv -o /dev/null https://projectarmillary.com/zh-TW/ 2>&1 | grep -iE "SSL connection|TLSv1"
技術依據

公開原始碼的 deploy/staging/nginx-site.conf.template：ssl_protocols TLSv1.2 TLSv1.3；ssl_ciphers ECDHE+AESGCM:ECDHE+CHACHA20（只有 ECDHE 金鑰交換與 AEAD 加密）；金鑰交換的簽章只接受 SHA-256 以上；TLS 工作階段票證（session ticket）關閉——票證金鑰一旦外洩，前向保密就打折。每次發布的主機驗收都確認 HSTS 存在，並確認 TLS 1.2 握手只用 SHA-256 以上的簽章。

界線：HSTS 目前沒有登記到瀏覽器內建的預載清單（preload）。從沒來過本站的瀏覽器，若手動輸入 http://，第一個請求在轉址前是明文——那個請求只有網址，不含出生資料；出生資料只會在加密連線上送出。

二、不追蹤

本站怎麼做
不設任何 cookie。前端程式不使用 localStorage、sessionStorage、IndexedDB、Cache Storage 或 beacon。沒有分析、廣告、錯誤追蹤或社群外掛。字型、圖片、樣式與程式全部由本站自己送出，不經過任何內容傳遞網路（CDN）。
擋住什麼
沒有分析、廣告或外部服務收到你的造訪紀錄——沒有 Google Analytics、沒有廣告聯播網、沒有外部字型服務。本站自己也沒有一個識別碼能把你今天和下週的造訪連起來。關掉分頁之後，瀏覽器的儲存區裡沒有出生資料；只有你自己按下的複製或下載會留在你的電腦上。
你怎麼查
〈親手驗證〉一步一步帶你用瀏覽器內建的開發者工具，看算一次盤送出的每一個請求、它們送到哪個網域，以及瀏覽器裡有沒有留下任何東西。終端機裡，下面這行不應印出任何東西： 
curl -sI https://projectarmillary.com/zh-TW/ | grep -i set-cookie
技術依據

出貨的前端程式裡沒有任何瀏覽器儲存或 beacon 的呼叫，後端程式沒有設定 cookie 的程式碼；瀏覽器流程測試在算盤並清除之後，讀回 localStorage 與 sessionStorage 都是空的。connect-src 'self'（見下一項）讓瀏覽器本身也拒絕把請求送到別的網域。

界線：瀏覽器會照一般規則暫存頁面與樣式檔（見第 06 節）；共用同一台電腦的人可以從瀏覽器快取看出這台電腦開過本站——瀏覽紀錄本來就看得出這件事；快取裡沒有出生資料，也沒有計算結果。

三、瀏覽器只准執行本站自己的程式

本站怎麼做
每個回應都帶內容安全政策（Content-Security-Policy，CSP）：script-src 'self' 只准執行本站網域上的程式檔；connect-src 'self' 頁面只能連回本站；frame-ancestors 'none' 本站不能被嵌進別人的網頁；再加上受信任類型（Trusted Types），禁止程式把任意字串當成 HTML 塞進頁面。頁面裡沒有內嵌的可執行程式。
擋住什麼
跨站腳本攻擊（cross-site scripting，XSS）是攻擊者把程式碼混進網頁、偷走你輸入的資料。在這裡，即使攻擊者找到注入點，瀏覽器也拒絕執行不是來自本站的程式，頁面發出的連線也只能回到本站。點擊劫持（clickjacking）——把本站嵌在透明框裡誘你點擊——也被擋掉。
你怎麼查
curl -sI https://projectarmillary.com/zh-TW/ | grep -i content-security-policy
完整的值與其他標頭列在第 06 節，和這行指令印出的應該一字不差。
技術依據

應用程式與反向代理送出同一組值（backend/app/privacy_logging.py 與 deploy/staging/nginx-site.conf.template，兩者都在公開原始碼裡），代理把應用程式的那一份藏起來、自己送一次，所以每個標頭只出現一次，連代理自己產生的錯誤頁也帶著。頁面裡唯一的 <script> 內嵌區塊是給搜尋引擎讀的結構化資料（JSON-LD），瀏覽器不執行它。

四、伺服器不記你的 IP，也不記出生資料

本站怎麼做
反向代理（nginx）的存取日誌關閉，錯誤日誌只記最嚴重的等級。應用程式每完成一個請求只寫一行事件，欄位固定 11 個（第 04 節列出全部）：路由類別、狀態碼，以及耗時與大小的「區間」——不是實際值。IP 位址、瀏覽器版本、網址參數、出生資料都不是欄位。主機的系統日誌保留上限 7 天或 50 MB，先到者為準；防火牆的封包紀錄關閉；當機傾印關閉。
擋住什麼
主機上沒有一份「誰在什麼時候查了什麼」的名單。沒有這份名單，就沒有東西可以外洩、被要求交出，或被拿來分析某個人。反向代理看得到你的 IP（不然回應送不回去），它只拿來做限流計數，不寫進日誌，也不轉送給應用程式。
你怎麼查
伺服器內部的日誌，你從外面看不到——這一項能查的是程式與設定：事件欄位由公開原始碼的 backend/app/privacy_logging.py 決定，第 04 節的表由同一份程式產生；存取日誌關閉寫在公開的 nginx 設定。每次發布時，我在主機上讀回：沒有存取日誌檔、防火牆紀錄裡沒有任何封包來源位址。
技術依據

事件在送出前再檢查一次欄位組合，多一個少一個都不輸出（第 04 節）。日誌保留的實際上限：主機日誌每小時換一個檔，所以一筆紀錄最長留 7 天再加約 1 小時。主機的日誌與防火牆設定目前不在公開原始碼裡，由發布時的主機驗收腳本讀回。

五、計算程式關在沒有對外網路的容器裡

本站怎麼做
計算服務跑在 Docker 容器裡：根檔案系統唯讀、以非 root 的一般使用者執行、Linux 能力（capabilities）全部移除、禁止取得新權限，記憶體、行程數與 CPU 都有上限。容器只接在一個沒有對外路由的內部網路上。
擋住什麼
如果計算程式或它用的函式庫有漏洞被利用，攻擊者拿到的是一個沒有網路出口、改不了程式檔、沒有特權的環境：資料送不出去，也沒有現成的權限可以拿來往主機擴大。
你怎麼查
公開原始碼的 deploy/compose.yaml 與 deploy/Dockerfile 逐行可查，數值列在第 08 節。每次發布前，我在實際要上線的映像上讀回：根檔案系統唯讀、有效能力為 0、no-new-privileges 開啟、執行身分不是 root。
技術依據

容器網路標記 internal: true：Docker 不替它建立對外路由。後端也沒有對外的 HTTP 客戶端，相依守衛偵測到這類套件就失敗（第 05 節）。真正擋住出口的是網路那一層，不是套件名單。

六、主機只開必要的門

本站怎麼做
主機防火牆預設拒絕所有連入，只開網頁用的 80／443 埠與管理用的 SSH。SSH 只接受金鑰登入，禁止密碼與 root 登入，而且只接受受限的來源位址。另一層防火牆規則對每個來源的新連線速度與同時連線數設上限。作業系統的安全更新每天自動安裝；Docker 本身例外，改由人工在可回滾的程序下更新，避免自動更新中斷服務。
擋住什麼
網路上隨時有程式在掃描主機、猜 SSH 密碼——這裡的 SSH 不收密碼，也不對一般來源開放，這類攻擊沒有對象。單一來源也無法只靠大量連線把網站拖垮；這能減輕、不能完全擋住來自大量來源的分散式攻擊。
你怎麼查
這一項大多只能在主機上查。每次發布時，主機驗收腳本讀回 SSH 實際生效的設定、每來源上限已載入、自動安全更新與日誌的設定檔和版控一致——任何一項不符，發布就停下；防火牆的預設政策與規則印在同一份驗收輸出裡，由我讀過確認。主機設定檔目前不在公開原始碼裡。

七、線上版本對得回公開原始碼

本站怎麼做
原始碼公開在 github.com/sa3952/Armillary。每張盤的〈計算收據〉印出這次用的後端映像識別碼（image ID）、前端發佈雜湊（artifact digest），以及兩者對應的公開原始碼修訂與網址。
擋住什麼
你不必只聽我說「線上跑的就是公開的那份」。前端——也就是在你瀏覽器裡實際執行的程式——任何人都能從公開原始碼重算出同一個雜湊，對照收據上的值。
你怎麼查
先從計算收據抄下前端的公開原始碼修訂，再到公開原始碼的 releases/<版本>/frontend-release.json 取得那一版的發佈紀錄。在那個修訂的乾淨 checkout 裡執行（需要 Python 與公開原始碼的開發相依）： 
python -m scripts.deployment.frontend_release recompute \
  --source-root . --release-record <下載的 frontend-release.json>
重建出的紀錄必須與公開的那份完全相同，印出的 artifact_digest 應等於收據上的前端發佈雜湊。
技術依據

每次發布前，我在公開原始碼的 checkout 上跑同一個指令，重建結果必須與要上線的紀錄相同，否則不發布。

界線：後端映像不是逐位元可重現——不同機器建出的檔案位元組可能不同。後端的對應是「原始碼對應」：鎖定雜湊的相依套件、釘選雜湊的基底映像、從原始碼建置的星曆函式庫與映像內的檔案清單，詳見公開原始碼的 docs/REPRODUCIBLE_BUILD.md。

02出生資料的完整路徑

請求內容
  → 請求範圍的資料模型（request-scoped，不跨請求存活）
  → 行程鎖底下的同步計算
  → 回應 ＋ 計算卷宗
  → 你的瀏覽器記憶體
  → （只有你按下時）剪貼簿或下載檔案

這條路徑上沒有任何一步寫入磁碟。守衛在請求處理期間替換 builtins.open、io.open 與 os.open；只要出現一次帶寫入旗標的呼叫，測試就失敗。

唯一的資料庫是內建的地名目錄，以唯讀、不可變模式開啟。它不含帳號或出生資料，也不寫入你打過的搜尋字串。

邊界

這說的是沒有主動寫入，不是安全抹除。計算期間資料存在於記憶體，之後由執行環境回收。守衛涵蓋的是 Python 層的寫入——原生函式庫的行為不在內。我不宣稱能從記憶體、swap 或當機傾印中抹除任何東西。

03五個信任邊界

威脅模型把系統切成五個邊界，每一個都假設對面是敵意的。這是內部文件的結構，不是為了這一頁編的。

A瀏覽器 → HTTP／ASGI攻擊者可控制 body、method、路徑、查詢字串、標頭、content-length、連線時序與畸形載荷。
B反向代理 → 應用程式應用程式不把邊緣傳來的任何值當成前提：方法、路徑、body 大小與併發上限一律由應用程式自己再判一次。邊緣的限制是額外一層，不是應用程式的保護來源。
C應用程式 → 星曆函式庫pyswisseph 使用行程全域狀態，因此同行程以鎖序列化。星曆檔與 C extension 是受信任但高影響的相依——不可把內部一致性當成外部天文驗證。
D瀏覽器 → 複製／下載使用者明示匯出後，資料離開應用程式記憶體。明示清除可使文件、區段、Blob URL 與請求世代失效，但撤不回已完成的複製或下載。
E部署與第三方代理、CDN、WAF、主機、遙測服務可能預設記錄網址、body、標頭或例外。在實際選型與設定驗證完成前，這個邊界一律視為不受信任。

要誠實說一件事：這份威脅模型成文於實際部署之前。邊界 E 已經有一部分變成現況，文件還沒完全追上。這是我自己知道的落差，不是被指出來才承認的。

04伺服器日誌的完整欄位

每完成一個請求輸出一行事件。欄位組合必須完全等於下表，多一個少一個都拒絕輸出。

{{telemetry_contract_rows}}
欄位允許的值

不會出現的東西：請求或回應內容、例外文字、堆疊追蹤、區域變數、查詢字串、完整網址、HTTP 標頭、cookie、authorization、呼叫端提供的請求 ID、IP 位址、User-Agent、referrer、出生時間、時區、地點、卷宗、計算軌跡、匯出內容。

失敗關閉

這不是靠事後過濾。事件由固定的建構函式產生，送出前再檢查一次欄位順序、版本、字彙與格式——把未清洗的資料送進輸出端會失敗關閉，該事件不會被輸出。外部送來的 request-id 標頭一律不採用。日誌輸出端本身故障時直接放棄該筆事件，不建立備援輸出端，也不影響你的回應。

05出口：結構上不可能，不只是政策

容器接在一個標記為 internal 的 Docker 網路上。internal: true 的意思是這個網路沒有對外路由——即使有程式想連出去，也沒有路可以走。

在那之上還有兩層：後端不含任何錯誤追蹤、APM、外部分析，也沒有對外的 HTTP 客戶端；相依守衛偵測到這類套件名稱就直接失敗。

前端不載入外部字型、CDN 腳本、第三方 JavaScript 或遠端圖片。地名搜尋走同源請求讀內建目錄，不使用瀏覽器定位、不使用 IP 定位、不呼叫任何線上服務。

這一段你可以自己檢查。〈親手驗證〉一步一步帶你用瀏覽器內建的開發者工具，看算一次盤送出的每一個請求、它們送到哪個網域，以及瀏覽器裡有沒有留下任何東西。

守衛的極限

相依守衛是針對已審查名單上的名稱所設的迴歸阻擋，不是完整的資訊流分析，不是遞移相依稽核，也不是執行期沙箱。名單外的新途徑仍需人工審查。真正擋住出口的是網路那一層，不是這份名單。

06送到你瀏覽器的標頭

應用程式對每個回應加上這一組；部署時由反向代理以相同的值統一送出，每個標頭只出現一次：

Cache-ControlAPI 與錯誤回應：no-store；頁面：no-cache（每次使用前向伺服器確認）；網址帶內容版本的樣式、程式與圖示檔：public, max-age=31536000, immutable；網址帶其他查詢參數：no-store

geolocation=() 是刻意的：連瀏覽器都被告知這個頁面不得使用定位，所以「本站不用定位」不只是承諾，是瀏覽器層級的封鎖。frame-ancestors 'none' 讓這個站不能被嵌進別人的 iframe。no-referrer 讓你從本站點出去的連結，不會告訴對方你從哪一頁來。

no-store 讓 API 回應與錯誤回應不進任何快取——出生資料只出現在這些回應裡。這一條由反向代理自己守住底線：/api 底下的所有回應、所有錯誤回應（4xx／5xx）、代理自己產生的回應（例如限流的 429），以及沒有帶快取指示的回應，一律送 no-store，即使應用程式出錯要求快取也一樣。

頁面與樣式、程式檔可以被瀏覽器暫存。頁面每次使用前都會向伺服器確認是否變過；網址帶內容版本（?v=，由檔案內容的雜湊算出）的樣式、程式與圖示檔，內容一變網址就變，所以可以長期暫存；版本不符或網址帶其他參數時不快取。/.well-known/security.txt 由代理直接提供，同樣每次確認。代價要說清楚：共用同一台電腦的人，可以從瀏覽器快取看出這台電腦開過本站——瀏覽紀錄本來就看得出這件事；快取裡沒有出生資料，也沒有計算結果。

反向代理另外加上 Strict-Transport-Security: max-age=31536000，加密協定只接受 TLS 1.2 與 1.3（第 01 節第一項）。公開測試（Public Alpha）期間，回應不帶 X-Robots-Tag：本站開放搜尋引擎收錄；個別頁面是否收錄，由頁內 robots 標記與 robots.txt 決定，兩者由同一份頁面清單產生。

前端不使用 localStorage、sessionStorage、IndexedDB、Cache Storage 或 beacon。敏感欄位標 autocomplete="off"——那是給瀏覽器的請求，不是它必須遵守的保證。

09壞掉的時候會怎樣

未預期的例外一律回傳固定錯誤代碼與伺服器產生的請求 ID，不回顯例外原文。星曆函式庫的錯誤回傳固定代碼，不回顯原始錯誤文字——那可能含本機路徑。

比較難的是回應已經開始送出之後才失敗。那時狀態碼已經在線路上，不能安全改寫。做法是：保留實際送出的狀態碼、把事件記為錯誤，並阻止原始例外進入框架自己的錯誤日誌。串流與背景工作的失敗路徑都有真實伺服器的反證測試。

匯出時 renderer 或 Blob 建立失敗，匯出面板必須顯示使用者看得見的錯誤，不能只留 console 或讓按鈕看似沒反應。

10兩個做過的判斷

控制清單看不出判斷力。下面兩件事仍屬於目前網頁產品，而且都包含我拒絕外部建議一部分的理由。

不可見字元：黑名單不會收斂，所以不用黑名單

地名欄位原本用列舉式 regex 擋不可見字元。實測發現 U+200B（零寬空格）、U+2028、U+2029、U+061C 全部漏過。

修補不是「再補幾個字元」——改以 Unicode general category 表達：Cc、Cf、Zl、Zp。這涵蓋上述全部，也涵蓋未來 Unicode 版本新增的格式字元。

但我拒絕了建議的一部分。報告主張把 ZWNJ（U+200C）與 ZWJ（U+200D）一併列為危險。那兩個字元在波斯文、阿拉伯文與印度系文字中是正字法必需的，用來選擇連寫或不連寫字形——封鎖它們是拒絕合法地名，不是拒絕敵意輸入。而且它們無法像 bidi 控制碼那樣重排已渲染的標籤，支撐這條邊界的顯示欺騙論證不及於它們。兩者明確豁免。

另外，錯誤訊息回報 U+XXXX 而不回顯該字元本身——避免把一個不可見或會翻轉方向的字元，放進一個將被其他介面渲染的字串。

「每執行緒一次」與「每請求一次」在原始碼裡分不出來

星曆初始化的意圖是每執行緒一次，程式卻寫成每請求一次——兩者在原始碼裡無從分辨，下一個讀者無法判斷哪個才是意圖。改用 threading.local 表達。

被拒絕的替代方案：用「已初始化的 thread ident 集合」會讓測試比較好寫，但 thread ident 在執行緒結束後會被重用，新執行緒會被誤判為已初始化——那正是這個機制要防的安靜錯誤。保留正確的機制，改讓測試配合。

12我最希望有人打破的地方

下面列出一組可直接拿來挑戰目前設計的代表問題。公開在這裡的理由很簡單：一份只列出自己擅長之處的安全頁沒有用。請在你自己的本機副本上試——公開原始碼可以在本機執行；SECURITY.md 不授權對正式服務做壓力測試或超出正常使用的掃描。

  • 編碼過的路徑、absolute-form URL、無效方法或標頭、chunked body，能否突破路由／方法／大小的縮減器？
  • ExceptionGroup、串流回應、背景工作、回應序列化失敗是否會外洩？CancelledError、KeyboardInterrupt、SystemExit、GeneratorExit 是否仍正確向上傳播？
  • Python logging 重設、handler 錯誤或重複 import，是否可能退回 root logger 並輸出未清洗的資料？
  • 執行期寫檔守衛是否漏掉 Path.write_*、原生寫入、快取、tempfile 或 fork？
  • 是否存在請求模型、全域變數、closure、快取或背景工作跨請求保留出生資料？
  • 清除之後殘留的 detached DOM handler、Blob URL、遲到回應或 back-forward cache，是否仍能還原資料？
  • 卷宗裡的證據引用，是否可能因測試改名或未重跑閘門而變成誤導？

威脅模型與原始碼一起公開；它按實際的信任邊界維護，不以本頁手抄的編號或數量作為是否最新的依據。

13相依與供應鏈

生產相依以帶雜湊的鎖定檔固定，另有軟體物料清單（SBOM）列出實際組成：Gate D 由映像以 syft 產生，與 lock 比對，保存在發佈收據中，與鎖定檔不一致即失敗。第三方原始碼封存檔、雜湊、授權與上游位置另有清單。

每次發布前，要上線的映像經過兩種已知漏洞（CVE）掃描：一種掃整個映像，一種專掃 Python 套件。高與嚴重等級的每一筆都要有逐項判定與複查期限，判定紀錄過期或有一筆未判定，發布就停下。這份判定紀錄目前不在公開原始碼裡。

相依套件、星曆檔與時區資料庫三者性質不同，各有自己的更新節奏與驗證步驟，不共用一套流程。星曆檔與恆星表的雜湊由測試直接驗證——有人替換了資料檔，測試會失敗。

邊界

這些是可查的程序與清單。它們不是供應鏈稽核，也不是對上游套件本身的安全保證。「已判定」的意思是我判斷該漏洞在本站的用法下碰不到——不是說映像裡沒有已知漏洞。

14我自己知道的攻擊面

這一節列的是真的可以拿來攻擊本站的東西，不是免責聲明。

  • 沒有專業滲透測試。應用層有具名外部技術審查與多工具對抗測試，每一輪的範圍與結果逐次留存。技術審查與滲透測試不是同一種證據。主機層另有供應商依合約每年執行的入侵測試（見〈信任〉層五）。
  • 沒有內容傳遞網路，也沒有應用防火牆。目前架構就是沒有這兩個元件。限流與連線上限在反向代理與主機防火牆，僅此而已；大量來源同時發動的分散式阻斷服務攻擊，可以讓網站暫時無法使用。
  • HSTS 還沒有加入瀏覽器的預載清單。從沒來過本站的瀏覽器，第一次以 http:// 連線時，轉址前的那個請求是明文；它只含網址，不含出生資料。
  • 沒有任何單一相依守衛算是完整控制。相依安全由直接輸入、雜湊鎖定的解析、SBOM、安裝集合回讀與執行期出口限制共同承擔；其中任何一項單獨都不足以宣稱安全。
  • 測試是設計期的迴歸證據，不在你每次計算時重跑。卷宗裡的證據欄位是指向測試的指標，不是「這一次執行過並通過」的紀錄。
  • 線上跑的版本不必然等於公開程式庫的最新版。要確認你正在用哪一版，看卷宗裡的版本識別碼——不要從最新提交推定，我自己也不這樣推定。
  • 主機設定只能由我讀回，你無法從外面核對。防火牆、SSH、日誌保留與自動更新的設定檔不在公開原始碼裡；每次發布時由主機驗收腳本讀回，結果沒有公開。
  • 隱私文案的依據是外部技術審查與主機上的實測驗證。技術審查與主機實測是不同證據，只涵蓋各自驗過的那一層，不互相代替，也不自動延伸到未涵蓋的層。

不能從「某個元件不存在」推論出「因此安全」。沒有 CDN 表示沒有 CDN 的攻擊面，也表示沒有 CDN 的防護。
